## 2. 关键发现：上游订阅当前本身不可达

启动测试实例后，后台刷新日志显示：

- 故障类型：**SSL 连接被远程主机强制关闭**（`SocketException 10054`），约 19–22 秒失败。
- 影响：**当前不存在“上游可达”状态**，因此“正常基线”无法采集；需待上游恢复后补测。
- 备用注入 URL 验证：`https://10.255.255.1/sub` 表现为 TLS 挂起约 21 秒后失败（挂起型），可作统一故障注入地址。

正常上游 URL（已备份，恢复时使用）：

```
https://fjsjjfzgud.684821.xyz/api/v1/client/subscribe?token=7d1d593e9ce3bf7d5963328e1f460c58
```

## 3. 串行基线（故障 + 冷缓存）

每个端点独立串行请求，记录 HTTP 状态与总耗时：

| 端点 | HTTP | 总耗时 | 说明 |
|---|---|---|---|
| `/`（仪表盘） | 200 | 19.29s | OnGet 内抓取失败被 catch，页面仍渲染（NodesError） |
| `/Config` | 200 | 19.28s | 仅一次抓取耗时（Raw 失败即进 catch，未叠加第二次） |
| `/Rules` | 200 | 19.35s | GetProxyGroups 抓取失败，页面渲染 GroupsError |
| `/sub?token=…` | 500 | 19.27s | 抓取失败抛 500 |

结论：**任何页面在订阅故障 + 冷缓存时都需等待约 19 秒**（对应 client.Timeout=30s 内连接被重置的时间），这就是“管理页面打不开”的直接体验。

## 4. 并发基线（故障 + 冷缓存）

### 4.1 5 个并发 `/sub`（锁路径 `_fetchLock`）

| 请求 | HTTP | 耗时 | 分析 |
|---|---|---|---|
| SUB3 | 500 | 19.58s | 第 1 个获锁，抓取 19s 失败 |
| SUB2 | 500 | 38.84s | 第 2 个获锁：排队 19s + 抓取 19s |
| SUB1 | 000 | >45s（curl 超时中断） | 锁队列排队，45s 内未获锁 |
| SUB4 | 000 | >45s | 同上 |
| SUB5 | 000 | >45s | 同上 |

结论：**静态信号量排队放大实证**——并发请求耗时按 N×19s 递增，第 3 个起超过 45 秒。

### 4.2 5 个并发 `/`（无锁路径）

| 请求 | HTTP | 耗时 |
|---|---|---|
| INDEX1 | 200 | 30.55s（疑似与后台刷新/网络抖动相撞） |
| INDEX2–5 | 200 | 19.67–20.09s |

结论：无锁路径**并行不排队**，但每个请求仍各自卡约 20 秒（重复抓取死连接）。

## 5. 基线结论（与修复目标对比）

| 指标 | 修复前（基线） | 阶段 1 目标 |
|---|---|---|
| 单请求故障耗时 | 约 19s（页面）/ 500（`/sub`） | ≤7s，页面渲染旧数据 |
| 并发排队 | N×19s（锁路径） | 无叠加，各自 ≤ 预算 |
| 数据可用性 | 故障时无任何数据（500/空） | 快照兜底 + 降级横幅 |

## 6. 局限与注意事项

1. **正常基线缺失**：上游当前故障，`正常网络下页面/抓取耗时` 未采集，上游恢复后需补测（用于校准 5s 超时是否误杀慢订阅）。
2. 测量期间后台刷新服务（周期 3 分钟）与请求存在偶发相撞（INDEX1 30.55s），基线含此干扰，符合真实使用场景。
3. 测试实例已停止；`Data/settings.json` 未做任何修改（上游本就故障，无需注入）。

## 8. 阶段 2 修复后对比（2026-09-09，故障路径）

> 改动：抓取收敛（Merged 复用 Raw 单一抓取路径 + 锁迁移至 Raw + 双重检查缓存）、锁等待超时（预算 +3s）、后台失败退避（×2 指数，封顶 ×8）。

### 8.1 并发压测对比（故障 + 冷缓存）

| 场景 | 阶段 1 | 阶段 2 |
|---|---|---|
| 5 并发 `/` | 各 ~5.4s 并行 | 锁竞争时 ~8.8s（锁等待 8s 超时快速失败，不再等待） |
| 10 并发 `/sub` | （阶段 1 时 5 并发即 3 个 >45s 中断） | **全部 ≤20.6s 返回**：2 个完成抓取（10.8s/20.6s），8 个 13s 锁超时快速失败 |

### 8.2 日志验证

## 9. 阶段 3 修复后对比（2026-09-09，故障路径）

> 改动：超时参数配置化（`AdminFetchTimeoutSeconds` / `PublicSubFetchTimeoutSeconds` 写入 `Data/settings.json`）、页面懒加载（服务端只读缓存，前端 JS 异步拉取 `/api/nodes`、`/api/groups`）、新增两个 API 端点、`/sub` 改用配置化超时。

### 9.1 页面加载耗时（故障 + 冷缓存）

| 端点 | 阶段 2 | 阶段 3 | 说明 |
|---|---|---|---|
| `/`（仪表盘） | 5.0s | **74ms** | OnGet 不再触发任何抓取，纯读缓存 + 本地存储 |
| `/Rules` | 5.15s | **90ms** | 同上；策略组由前端 JS 异步拉取 |
| `/sub` | 10.0s / 500 | **10.2s** / 500 | 仍按配置超时（10s）快速失败，无快照时 500 |

### 9.2 懒加载 API 端点（故障 + 后台刷新持锁窗口）

| 端点 | 返回 | 行为 |
|---|---|---|
| `/api/nodes` | 200 `{"ok":false,"error":"等待订阅抓取锁超时（8s）…"}` | 锁等待按预算（5s+3s）截断，不阻塞 |
| `/api/groups` | 200 `{"ok":false,"error":"A task was canceled."}` | 请求超时（5s）取消锁等待，快速失败 |

> 页面渲染不依赖这两个 API：失败时节点卡片显示"无法加载节点信息"占位，页面本身已秒开。缓存命中时 API 直接返回数据，不触碰抓取锁。

### 9.3 配置化验证

- `Data/settings.json` 新增字段：`adminFetchTimeoutSeconds`（默认 5）、`publicSubFetchTimeoutSeconds`（默认 10），`[Range(1,60)]` 校验。
- 设置页新增「超时配置」卡片，两个输入框随表单提交；`OnPostSaveAsync` 绑定自动生效。
- `/sub` 端点从静态 `ClashSubService.PublicSubFetchTimeout` 改为读取配置（实测 10.2s ≈ 配置 10s）。

### 9.4 页面行为

- 首页节点卡片与规则页策略下拉均**常驻渲染**；服务端缓存命中直接内联，未命中由 JS 拉取 `/api/nodes`、`/api/groups` 动态填充。
- 降级横幅（stale）逻辑不变，故障时仍正确提示"订阅数据不可用"。

### 9.5 待上游恢复后补测项

- 正常网络下懒加载端到端：缓存命中 → 页面内联数据；缓存过期 → JS 异步拉取最新节点/策略组，页面无感刷新。
- 正常网络全功能回归（节点测速/规则合并/导入/设置保存）。
